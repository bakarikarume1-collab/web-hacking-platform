Web Hacking Fundamentals

Before learning SQL Injection, Cross Site Scripting, or Remote Code Execution, every security engineer must understand how web applications communicate.

Beginner Level

Introduction to Web Hacking

Web hacking is the process of identifying, understanding, and responsibly testing weaknesses found in web applications. Modern websites are built using browsers, servers, databases, and APIs. Every action you perform, such as logging in, searching, or uploading a file, is converted into HTTP requests. Understanding these requests is the first skill of every penetration tester.

Professional Tip

A professional hacker rarely attacks a website immediately. Instead, they spend most of their time understanding how the application behaves, what technologies it uses, and where user input reaches the backend.

Understanding HTTP

HTTP (HyperText Transfer Protocol) is the protocol responsible for communication between a client (browser) and a web server. Every webpage, image, video, login request, or API request travels using HTTP or HTTPS.

Example HTTP Request



GET /index.html HTTP/1.1

Host: example.com

User-Agent: Chrome

Accept: text/html

The browser sends this request to the server. The server processes it and returns an HTTP Response.

HTTP Request vs HTTP Response

Request Response
Sent by Browser Sent by Server
Contains Method Contains Status Code
Contains Headers Contains Headers
Contains Body Contains HTML or JSON

HTTP Methods

  • GET → Retrieve information
  • POST → Send new information
  • PUT → Replace existing data
  • PATCH → Update part of data
  • DELETE → Delete information

Security Note

Many broken access control vulnerabilities occur because developers forget to verify whether a user is allowed to use dangerous HTTP methods like PUT or DELETE.

Anatomy of an HTTP Request

Every HTTP request is made of four main parts: Request Line, Headers, Empty Line, and Body. Understanding this structure is essential for web security testing.

1. Request Line


GET /login HTTP/1.1

This line contains:

  • HTTP Method (GET, POST, etc.)
  • Request Path (/login, /api/user)
  • HTTP Version (HTTP/1.1 or HTTP/2)

Security Insight

Attackers often change HTTP methods (GET → POST → PUT) to bypass weak access controls.

HTTP Headers

Headers are key-value pairs that describe the request. They carry important metadata between client and server.

  • Host → Target domain
  • User-Agent → Browser or tool identity
  • Cookie → Session identifier
  • Authorization → Login tokens (JWT, Bearer)
  • Content-Type → Format of request body

Real Attack Scenario

Changing the User-Agent can bypass simple WAF filters because some systems block only known tool signatures like sqlmap.

Cookies & Sessions

HTTP is stateless — meaning the server does not remember users. Cookies solve this problem by storing session identifiers.

Example Cookie


Cookie: session_id=abc123xyz

If an attacker steals this cookie, they can impersonate the user without a password.

Important Note

Weak session generation (like incremental IDs) can allow attackers to guess valid sessions.

Introduction to Burp Suite

Burp Suite is a web security testing tool used to intercept and modify HTTP traffic.

Main Features

  • Proxy → Intercept requests
  • Repeater → Modify and resend requests
  • Intruder → Automated attacks (fuzzing, brute force)

How It Works

Burp Suite acts as a Man-in-the-Middle (MITM) between browser and server, allowing full control of requests before they reach backend.

Client-Side Validation Weakness

Frontend validation (HTML + JavaScript) is NOT security. It can be bypassed easily using browser tools or intercepting proxies.

Example

Even if the browser limits input to 500, an attacker can modify the request using Burp Suite and send any value to the server.

The Empty Line (CRLF)

After HTTP headers, there is always a mandatory empty line. This is called CRLF (Carriage Return Line Feed). It tells the server that headers have ended and body begins. 


GET /login HTTP/1.1
Host: example.com
User-Agent: Chrome

(username and password start here)

Security Insight

Improper parsing of CRLF can lead to HTTP request smuggling vulnerabilities.

HTTP Message Body

The body contains data sent to the server. It is mostly used in POST, PUT, and PATCH requests.

Example POST Request


POST /login HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

username=admin&password=12345

This is where user input becomes dangerous. Most vulnerabilities like SQL Injection and XSS originate from request bodies.

Full HTTP Request Flow

When you click a button on a website, the following happens:

  • Browser builds HTTP request
  • Request is sent to server
  • Server processes input
  • Database may be queried
  • Response is returned
  • Browser renders result

Attacker Perspective

A hacker intercepts this flow using tools like Burp Suite, modifies the request before it reaches the server, and observes how backend reacts.

Mini Practical Scenario

Imagine a login system: 


POST /login HTTP/1.1
username=admin
password=admin123

If the application does not properly validate input, an attacker may manipulate the request to bypass authentication or inject SQL payloads.

Summary of Basics

  • HTTP is stateless communication protocol
  • Requests have 4 main parts
  • Headers carry metadata
  • Cookies store sessions
  • Body contains user input
  • Everything can be intercepted using proxies
